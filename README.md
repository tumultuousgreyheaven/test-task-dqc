# Сервис контроля качества данных (ККД)

## Запуск, тесты и проверка миграций

### Запуск всего проекта в контейнере
```
cp .env.example .env
docker compose up --build
```
По умолчанию запускается профиль demo с тестовыми данными в БД. Отключить его можно убрав `demo` из `SPRING_PROFILES_ACTIVE` в .env.

### Запуск тестов
```
./mvnw test
```

Unit-тесты на JUnit 5 находятся в `src/test/java`. Они проверяют граничные случаи четырёх правил,
расчёт метрик и каскадирование, округление и тренды, идентичность проблем между прогонами,
валидацию фильтров и пагинацию, формирование сводки по дереву подразделений и запуск нового прогона.
HTTP-сервер и PostgreSQL для этих тестов не требуются.

### Проверка миграций
```
./scripts/check-migrations.sh
```

## Архитектура

Сервис реализован в соответствии с DDD. Предметная область реализована в слое (пакете) `domain`. Здесь находится логика правил (`domain.rule`),
метрики и их вычисление (`domain.metric`), дельты и их вычисление (`domain.delta`). Предметная область не зависит от фреймворка; она не знает о
существовании БД и REST-контроллера.

### Логика правил

Интерфейс `QualityRule` содержит три метода: `code` (кодовое название правила, `String`), `severity` (серьёзность правила, enum `Severity`) и
`check` (поиск нарушений правил в загруженных данных `QualitySnapshot`). \
Интерфейс реализуется базовым абстрактным классом `BaseQualityRule`. Реализуются методы `code` и `severity` (поскольку их поведение одинаково
для всех правил), `check` остаётся не реализованным. Добавлены также два `protected static` метода, конструирующие объект `Finding` (находка
нарушения правила в загруженных данных) с заданными параметрами: один из них возвращает находку нарушения в цели, второй - в КР. \
Базовый класс наследуется четырьмя классами-правилами; в каждом из них метод `check` реализован по своему. \
Реализованы четыре правила из данных в ТЗ: `GOAL_NO_OWNER`, `GOAL_NO_KR`, `KR_WEIGHTS_SUM` и `KR_NO_TARGET`. В каждом классе реализован метод
`check`, производящий поиск по активным целям из `QualitySnapshot`. \
Движок `RuleEngine` загружает в себя коллекцию правил; методом `run` он производит поиск нарушений по всем загруженным правилам по `QualitySnapshot`.
Движок регистрируется как Spring-бин в классе `infrastructure.config.DomainConfiguration`.

### Метрики

Интерфейс `QualityMetric` содержит пять методов: `key` (уникальный ключ метрики, `String`), `title` (краткое описание, `String`), `unit` (единица
измерения метрики, `String`), `higherIsBetter` (является ли повышение метрики улучшением качества, `boolean`) и `measure` (вычисление метрики
для каждого подразделения без учёта дочерних, `Map<String, Ratio>`). \
Реализовано три метрики:
- `cascade_clean_share` - доля целей без проблем в цепочке вышестоящих
- `clean_goals_share` - доля корректных целей
- `kr_with_target_share` - доля КР с заполненным целевым значением

Все три метрики являются долями, в связи с чем единица измерения у всех - проценты; улучшение качества данных отражается ростом каждой из них.
Числовая величина метрики реализована специальным классом `Ratio`. Метод `percent` возвращает процентное значение `Ratio` в виде `BigDecimal`,
либо `Optional.empty()`, если знаменатель нулевой. Для подсчёта отношений реализован класс `RatioAccumulator`. \
`MetricCalculator` с помощью метода `calculate` вычисляет все реализованные метрики по `QualitySnapshot` и списку найденных проблем `List<Issue>`.
Метод возвращает `List<MetricValue>` - итоговые значения (в виде `Ratio`) всех метрик по всем подразделениям. `MetricCalculator` регистрируется
как Spring-бин в `infrastructure.config.DomainConfiguration`. \
В пакете `domain.metric` так же реализован класс `MetricComparator`, который статическим методом `compare` сравнивает `Ratio` метрики между двумя
прогонами. Возвращает объект `MetricReading` - результат по метрике, содержащий значение в предыдущем и текущем прогоне (`BigDecimal`), дельту и
тренд (enum `Trend`: лучше, хуже или так же). \

### Дельты

Вычисление дельт по метрикам реализуется в `MetricComparator`. Вычислением же дельт по нарушениям правил занимается класс `IssueDeltaCalculator`.
Метод `calculate` принимает коллекции `Issue` в текущем прогоне и предыдущем. Текущие `Issue` метод разбирает на появившиеся вновь и оставшиеся с
прошлого прогона. Старые `Issue`, не найденные среди новых, метод записывает в решённые. Новые, оставшиеся и решённые проблемы метод записывает в
record-класс `IssueDelta`. \
Прогоны, найденные проблемы и вычисленные метрики реализованы как таблицы в БД. В таблице прогонов в каждой строке есть id предыдущего прогона (у
самого первого прогона он NULL). Для вычисления дельт из БД вместе с выбранным прогоном загружается предшествующий ему.
