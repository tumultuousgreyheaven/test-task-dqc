# Требования к решению задачи

## Задача

Разработать сервис контроля качества данных (далее – ККД) на Java: проверку качества данных по целям и ключевым результатам, хранение результатов в PostgreSQL и REST API для страницы ККД.

## Подзадачи и требования к решению

- Спроектировать схему БД: подразделения с иерархией, цели (ответственный, родительская цель, статус, срок) и ключевые результаты (целевое и фактическое значение, вес, дата обновления факта); плюс таблицы результатов ККД: справочник правил, прогон и найденная проблема.

- Реализовать четыре правила проверки качества целей и ключевых результатов (КР):
  GOAL_NO_OWNER — цель без ответственного (critical);
  GOAL_NO_KR — у активной цели нет ни одного ключевого результата (critical);
  KR_WEIGHTS_SUM — сумма весов КР цели не равна 100% (major);
  KR_NO_TARGET — у КР не заполнено целевое значение (major).
  Уровни важности: critical, major, minor. Правила применяются только к активным целям и их КР.
  Логику правил держать отдельно от слоя API и доступа к данным — отдельным компонентом, который получает данные и возвращает список найденных проблем.

- Разработать три простые метрики, позволяющие количественно оценить качество данных. При расчёте метрик должно учитываться каскадирование целей.

- Загрузить стартовые данные: 20–30 целей в двух-трёх подразделениях и два прогона — так, чтобы были нарушения каждого правила и было с чем сравнивать.

- Миграции — Liquibase или Flyway с откатом: накат → откат → повторный накат без ошибок (в проекте это условие приёмки на общем тестовом стенде).
  Весь проект поднимается одной командой `docker compose up` — сервис, PostgreSQL, миграции и стартовые данные.

- Реализовать `GET /api/runs` — список прогонов: статус, дата снимка, с каким прогоном сравнивается, число найденных проблем.

- Реализовать `GET /api/kkd/summary?run_id=&unit_id=` — минимум три метрики по подразделению с текущим и прошлым значением, дельтой и признаком «лучше / хуже», разбивка проблем по важности и счётчики новых, сохраняющихся и исправленных.
  Метрики подразделения считаются с учётом дочерних, формат ответа — смотри в файле summary-response-format.json.

- Реализовать `GET /api/kkd/issues` — список проблем прогона с фильтрами по подразделению, правилу и важности и пагинацией (limit, offset, total).

- Дельта: проблема «та же самая», что и в прошлом прогоне, если совпадают правило и объект.
  У первого прогона сравнения нет — прошлые значения и дельта равны null, а не 0.

- Проверки: неизвестный прогон или подразделение — 404, некорректные параметры — 422.
  Формат ошибки единый: `{"error": {"code": "...", "message": "..."}}`.

- Покрыть тестами (JUnit 5) минимум 4 сценария: два правила на граничных данных, расчёт метрики и расчёт дельты. Поднимать HTTP не требуется.

## Технические требования

Стек: Java 17+, Spring Boot 3, PostgreSQL 15+, Liquibase или Flyway, Maven. \
Конфигурация через переменные окружения (.env.example), корректные HTTP-статусы, валидация входных параметров, контроллеры отделены от сервисного слоя и доступа к данным.

## Условия приёма

- Решение в виде кода оформлено в соответствии с требованиями
- Сервис корректно собирается, все тесты успешно проходятся
- Скрипты БД корректно выполняются (накат – откат – повторный накат)
