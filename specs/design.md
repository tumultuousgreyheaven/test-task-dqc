# Проектирование сервиса контроля качества данных (ККД)

Документ описывает модель данных, API и ключевые проектные решения. Архитектура слоёв `domain` описана в README; здесь она
упоминается только там, где от неё зависят решения по данным и API.

## Модель данных

Схема создаётся миграциями Liquibase (`db/changelog/changes/`, формат formatted SQL). У каждого changeset есть блок `--rollback`,
поэтому накат, откат и повторный накат выполняются без ошибок (проверка: `scripts/check-migrations.sh`). Таблицы делятся на две
группы: исходные данные (подразделения, цели, КР) и результаты ККД (справочник правил, прогоны, проблемы, значения метрик).

### Исходные данные

`org_unit` - подразделения. Иерархия задаётся полем `parent_id` (ссылка на ту же таблицу, у корневого подразделения `NULL`).
Ограничение запрещает подразделению быть собственным родителем.

`goal` - цели. Поля: `id`, `unit_id` (подразделение), `title`, `owner` (ответственный), `parent_goal_id` (вышестоящая цель,
каскадирование), `status`, `due_date`. Статус - одно из `draft`, `active`, `achieved`, `cancelled`; правила ККД применяются только к
`active`.

`key_result` - ключевые результаты цели. Поля: `id`, `goal_id`, `title`, `target_value` (целевое значение), `actual_value` (факт),
`weight` (вес в процентах, от 0 до 100), `fact_updated_at` (дата обновления факта). КР удаляются вместе со своей целью (`ON DELETE CASCADE`).

Ограничения на этих таблицах намеренно мягкие там, где качество данных проверяют правила ККД: `owner` и `target_value` могут быть `NULL`,
сумма весов КР цели базой не контролируется. Если бы схема не допускала нарушений, проверять было бы нечего.

### Результаты ККД

`kkd_rule` - справочник правил: `code` (первичный ключ, совпадает с `QualityRule.code()`), `title`, `description`, `severity`,
`is_active`. Строки заводятся миграцией `004-kkd-rules-data.sql`.

`kkd_run` - прогоны. Поля: `id` (вида `RUN-008`), `snapshot_date`, `status` (`running`, `completed`, `failed`),
`compared_to_run_id` (прогон, с которым сравнивается этот; у первого прогона `NULL`), `started_at`, `finished_at`. Идентификатор
формируется из последовательности `kkd_run_seq` и дополняется нулями до трёх знаков.

`kkd_issue` - проблемы, найденные в прогоне. Поля: `run_id`, `rule_code`, `severity`, `object_type` (`goal` или `key_result`),
`object_id`, `goal_id` (цель, к которой относится проблема; для КР - его цель), `unit_id`, `message`. Ограничение
`UNIQUE (run_id, rule_code, object_type, object_id)` не даёт правилу найти одну и ту же проблему в одном объекте дважды.
Проблемы удаляются вместе с прогоном.

`kkd_metric_value` - значения метрик. Первичный ключ `(run_id, unit_id, metric_key)`, значение хранится как `numerator` и
`denominator`. Ограничение требует `0 <= numerator <= denominator`.

### Решения по модели

**Проблема - снимок.** В `kkd_issue` важность, подразделение и цель фиксируются на момент прогона. Если цель потом перейдёт в другое
подразделение или правило сменит важность, старые прогоны останутся такими, какими были. По той же причине `object_id` и `goal_id`
не имеют внешних ключей: объект может быть удалён позже, а история прогона должна сохраниться.

**Метрики хранятся как числитель и знаменатель.** Значение подразделения с дочерними - это сумма числителей, делённая на сумму
знаменателей. Среднее процентов по дочерним подразделениям было бы неверным (маленькое подразделение весило бы как большое). Поэтому
в таблице лежат доли только по собственным объектам подразделения, а сумма по поддереву считается при чтении.

**Метрики пишутся для каждого подразделения, включая 0/0.** Тогда отсутствие строки у прошлого прогона однозначно означает "метрика
тогда не считалась" (в API это `previous = null`), а не "объектов не было".

**Идентичность проблемы между прогонами.** Проблема в двух прогонах считается "той же самой", если совпадают правило и объект
(`rule_code`, `object_type`, `object_id`). Текст сообщения, важность и подразделение в сравнении не участвуют.

**Связь с предыдущим прогоном хранится в самом прогоне** (`compared_to_run_id`). Прогон на дату D сравнивается с последним завершённым
прогоном, у которого дата снимка строго раньше D. Поэтому повторный запуск на ту же дату не сравнивается сам с собой.

**Справочник правил проверяется при старте.** Приложение сверяет правила, реализованные в коде, со строками `kkd_rule`: у каждой
реализации должна быть строка с той же важностью, у каждой включённой строки (`is_active = true`) - реализация. При расхождении
приложение не стартует. Правило с `is_active = false` не применяется; состав правил читается один раз при старте, поэтому изменение
флага требует перезапуска.

**Индексы** подобраны под запросы API: `kkd_run (snapshot_date DESC)` для списка прогонов, `kkd_issue (run_id, unit_id)` и
`kkd_issue (run_id, severity)` для списка проблем и сводки.

## API

Все ответы - JSON, имена полей в `snake_case`. Для всех ошибок единый формат: `{"error": {"code": "...", "message": "..."}}`.

### GET /api/runs

Список прогонов, новые первыми (по дате снимка, затем по времени запуска). Параметров нет.

```json
{
  "items": [
    { "id": "RUN-008", "snapshot_date": "2026-10-26", "status": "completed", "compared_to_run_id": "RUN-007", "issue_count": 14 },
    { "id": "RUN-007", "snapshot_date": "2026-10-19", "status": "completed", "compared_to_run_id": null, "issue_count": 14 }
  ]
}
```

### POST /api/runs

Запускает ККД по текущим данным и возвращает созданный прогон (`201`, поля те же, что в списке). Тело необязательно:
`{"snapshot_date": "2026-10-26"}`; без даты берётся сегодняшняя. Дата не может быть в будущем и раньше даты последнего завершённого
прогона (иначе `422`).

### GET /api/kkd/summary

Сводка по подразделению вместе со всеми его дочерними подразделениями.

| Параметр | Обязательный | Описание |
|---|---|---|
| `unit_id` | да | подразделение |
| `run_id` | нет | прогон; по умолчанию последний завершённый |

```json
{
  "run": { "id": "RUN-008", "snapshot_date": "2026-10-26" },
  "compared_to": { "id": "RUN-007", "snapshot_date": "2026-10-19" },
  "unit": { "id": "HQ-CIB", "name": "Департамент корпоративного бизнеса" },
  "metrics": [
    { "key": "cascade_clean_share", "title": "Доля целей без проблем в цепочке вышестоящих", "unit": "%",
      "value": 37.5, "previous": 12.5, "delta": 25.0, "trend": "better" },
    { "key": "clean_goals_share", "title": "Доля корректных целей", "unit": "%",
      "value": 62.5, "previous": 37.5, "delta": 25.0, "trend": "better" },
    { "key": "kr_with_target_share", "title": "Доля КР с заполненным целевым значением", "unit": "%",
      "value": 94.4, "previous": 87.5, "delta": 6.9, "trend": "better" }
  ],
  "issues_by_severity": [
    { "code": "critical", "current": 2, "previous": 2, "delta": 0 },
    { "code": "major", "current": 2, "previous": 4, "delta": -2 },
    { "code": "minor", "current": 0, "previous": 0, "delta": 0 }
  ],
  "delta": { "new": 1, "persisting": 3, "resolved": 3 }
}
```

- Метрики идут в порядке ключей. `trend` принимает значения `better`, `worse`, `same` и учитывает, в какую сторону метрика
  улучшается.
- `issues_by_severity` всегда содержит все три уровня важности, в том числе с нулями.
- У первого прогона сравнивать не с чем: `compared_to`, `previous`, `delta` (в метриках и по важности), `trend` и весь блок `delta`
  равны `null`, а не нулям. То же для метрики, у которой в прошлом прогоне не было значения. Если у подразделения нет объектов, по
  которым метрика считается, `value` тоже `null`, а не 0.
- Значения процентов округляются до одного знака (`HALF_UP`), а `delta` - это разность уже округлённых значений, чтобы цифры в ответе
  сходились (62.7 → 56.5 даёт -6.2).

### GET /api/kkd/issues

Список проблем прогона.

| Параметр | Описание |
|---|---|
| `run_id` | прогон; по умолчанию последний завершённый |
| `unit_id` | подразделение вместе с дочерними; по умолчанию все |
| `rule` | код правила, например `GOAL_NO_OWNER` |
| `severity` | `critical`, `major` или `minor` |
| `limit` | размер страницы, от 1 до 200, по умолчанию 50 |
| `offset` | смещение, не меньше 0, по умолчанию 0 |

Пример для `GET /api/kkd/issues?run_id=RUN-008&unit_id=HQ-CIB&severity=critical&limit=1`:

```json
{
  "items": [
    { "rule_code": "GOAL_NO_OWNER", "severity": "critical", "object_type": "goal", "object_id": "G-010",
      "goal_id": "G-010", "unit_id": "HQ-CIB", "message": "У цели G-010 «Рост корпоративного кредитного портфеля» не назначен ответственный" }
  ],
  "total": 2,
  "limit": 1,
  "offset": 0
}
```

Порядок: важность (от `critical` к `minor`), код правила, тип и идентификатор объекта. `total` - число проблем, подходящих под фильтры,
без учёта `limit` и `offset`.

### Ошибки

| Статус | `error.code` | Когда |
|---|---|---|
| 404 | `RUN_NOT_FOUND` | нет такого прогона, или нет ни одного завершённого |
| 404 | `UNIT_NOT_FOUND` | нет такого подразделения |
| 409 | `RUN_NOT_COMPLETED` | прогон ещё не завершён |
| 422 | `INVALID_PARAMETER` | не указан `unit_id`; `limit` и `offset` вне диапазона или не числа; неизвестные `severity` и `rule`; неверная дата или тело запроса |
| 404 | `NOT_FOUND` | неизвестный адрес |
| 405 | `METHOD_NOT_ALLOWED` | метод не поддерживается адресом |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | тело запроса не в формате JSON |
| 500 | `INTERNAL_ERROR` | непредвиденная ошибка; подробности только в логе, клиент получает общий текст |

Параметры запроса проверяются раньше, чем ищутся прогон и подразделение: `GET /api/kkd/issues?run_id=RUN-999&severity=urgent`
вернёт `422`, а не `404`.

## Слои и поток данных

Зависимости направлены внутрь: `api` -> `application` -> `domain`; слой `infrastructure` реализует интерфейсы, объявленные в
`application`, и содержит конфигурацию.

- `api` - контроллеры (`RunController`, `KkdController`), DTO и единый обработчик ошибок. Только разбор запроса и формирование
  ответа, никакой логики.
- `application` - сервисы (`RunService`, `RunQueryService`, `SummaryService`, `IssueQueryService`), интерфейсы репозиториев,
  исключения. Здесь же проверяются параметры запроса, чтобы ошибки выглядели одинаково и сервисы работали без HTTP.
- `domain` - правила, метрики, дельты; чистая Java без Spring.
- `infrastructure` - реализации репозиториев на `JdbcClient`, регистрация правил и метрик, часы, загрузчик демо-данных.

Запуск ККД (`RunService.start`) состоит из шагов: определить предыдущий прогон, создать прогон, загрузить `QualitySnapshot` из БД,
применить `RuleEngine`, посчитать метрики `MetricCalculator`, сохранить проблемы и метрики, отметить прогон завершённым. Сводка
(`SummaryService`) читает прогон и предшествующий ему, суммирует метрики по поддереву подразделения, сравнивает их через
`MetricComparator`, а проблемы - через `IssueDeltaCalculator`.

## Ключевые решения

**Spring JDBC (`JdbcClient`), а не Spring Data JDBC.** Данные - это снимки и агрегаты, а не граф сущностей с жизненным циклом. Запросы
(фильтры по подразделениям, пагинация, пакетная вставка) проще и прозрачнее писать на SQL; маппинг строк в доменные записи явный. Доменные
классы не зависят от аннотаций персистентности.

**Автоматическая регистрация правил и метрик.** `DomainConfiguration` сканирует пакеты `domain.rule` и `domain.metric` и подбирает
любой конкретный класс, реализующий `QualityRule` или `QualityMetric`. Чтобы добавить правило или метрику, достаточно написать класс
с конструктором без аргументов и добавить строку правила в `kkd_rule`; в домене по-прежнему нет ни одной Spring-аннотации.

**Репозитории объявлены в `application`, реализованы в `infrastructure`.** Сервисы зависят от интерфейсов, а не от JDBC; реализации
можно подменить в тестах.

**Каскадирование.** Метрика `cascade_clean_share` считает цель корректной, только если нет проблем ни у неё самой, ни у любой
вышестоящей цели по цепочке `parent_goal_id`. Неактивная цель в цепочке сама проблем не имеет (правила её не проверяют), но цепочка
через неё продолжается. Циклы в данных обрываются. Значение метрики не больше `clean_goals_share`, а разница - это "унаследованный" брак.

**Весь прогон - одна транзакция** (`REPEATABLE READ`): при ошибке не остаётся ни прогона, ни половины его результатов, а три запроса
загрузки снимка видят согласованные данные. Следствие: статусы `running` и `failed` в обычной работе не наблюдаются, снаружи видны
только завершённые прогоны. Чтение с запросами к нескольким таблицам тоже идёт в `REPEATABLE READ`, чтобы `total` и страница
согласовывались.

**Незавершённый прогон не читается**: запрос по нему возвращает `409`, а выбор прогона по умолчанию его пропускает.

**Снимок - это текущее состояние данных.** `snapshot_date` - метка прогона, а не момент, на который восстанавливаются данные:
история изменений целей и КР в БД не хранится. Поэтому дата не может быть в будущем и не может быть раньше последнего завершённого
прогона.

**Демо-данные** загружаются при первом запуске с профилем `demo` (`DemoDataLoader`). Это два SQL-скрипта (`resources/demo/`): данные
недели 7 и изменения недели 8; между ними загрузчик через настоящий `RunService` делает прогоны RUN-007 и RUN-008. В данных заложены
нарушения всех четырёх правил, граничные случаи (пустой и состоящий из пробелов ответственный, целевое значение 0, веса 33.33 x 3),
неактивные цели с нарушениями и цели с "грязными" родителями. Загрузка идёт одной транзакцией и пропускается, если в БД уже есть
подразделения или прогоны.

## Ограничения

- Нет авторизации и разграничения доступа.
- Параллельные запуски `POST /api/runs` не сериализуются: два одновременных запроса могут выбрать один и тот же предыдущий прогон.
- Список прогонов отдаётся целиком, без пагинации.
- Все метрики - доли в процентах; метрика с другой единицей измерения потребует расширения `Ratio`.
